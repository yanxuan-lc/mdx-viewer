## 新增：`mdxv --check`，交付前先校验能否编译

`mdxv` 起得来**不等于**文档编译得过。MDX 编译是惰性的，只在浏览器 import 该模块时才发生，
所以一篇写坏的文档照样能拿到绿色的「预览就绪」横幅和一个打开就 500 的 URL——把这个 URL 交给
别人之前，你没有任何信号。

```bash
mdxv --check doc.mdx   # 校验单篇
mdxv --check ./docs    # 校验目录下每篇 .md/.mdx，逐条报告
mdxv --check demo      # 校验随包内置示例
make check-mdx FILE=<file|dir>   # 从源码使用时的等价入口
```

它用**本项目自己的 `mdxOptions()`** 逐篇编译，不起服务、不写任何产物：

| 退出码 | 含义 |
|---|---|
| `0` | 全部通过 |
| `1` | 至少一篇文档编译失败 |
| `2` | 校验本身没能执行（用法/入参错误、文档集为空） |

报告写 **stdout**，`Error:` 诊断写 **stderr**，所以 `mdxv --check ./docs >report 2>err` 能把
「文档坏了」和「你调用错了」分开，且 report 里**逐字节不含 ANSI 颜色码**——消费方不需要在管道上
挂剥色正则。比过去拿 `mdxx` 导出当校验的土办法快约 **10 倍**。

`format` 按每篇文档的扩展名逐篇推导，所以 `.md` **不会**被当成 MDX 解析——一份行首是 `<` 的
合法 `.md` 不会被误判成失败。

**边界（请当成机制读，不要当成清单）**：通过意味着这篇文档**打得开**，不意味着它是对的。
未定义组件、非法属性值、畸形数学都能加载但渲染不对；任何顶层 ESM 语句或 `{…}` 表达式在模块
求值 / 渲染期失败，会让文档根本加载不出来，而这些本命令检不出。围栏代码块里的 `import` 是纯
文本，所以「写文档讲 JavaScript」完全不受影响。`--check` 与 `--help` / `--version` 组合时，
后两者优先。

编译**从不求值**文档代码（表达式经 acorn 解析后原样发出，frontmatter YAML 用安全默认 schema），
所以对机器生成的文档也可以无人值守地跑。

## 修复：图里的颜色跟随明暗主题

深色主题下 `dot` 图的框线变白、框内文字仍是黑的、背景透明，于是**文字直接消失**。根因是
Graphviz 的 `<text>` 不写 `fill`，而 SVG 规范里 `fill` 的初始值是 `black` 而不是 `currentColor`，
所以在容器上写 `color` 救不到它。旧实现在字符串上用正则替换三种黑色写法，既认不全写法
（`hsl(0,0%,0%)`、`#000f`、`rgb(0 0 0)` 都是纯黑却漏判），也认不出「完全不写 `fill`」这一种。

现在改在 hast 层做，`dot` 与 `svg` 两车道共用，`mdxv`（预览）与 `mdxx`（导出）两条路径自动一致。
深浅两主题下图内文字对比度实测 13.42:1 / 13.84:1（WCAG AAA 的门槛是 7:1）。

顺带修掉两个既有缺陷：

- **具名图的白底再也不残留。** `digraph G { … }` 会在中间插一个 `<title>`，旧的按位置锚定的
  正则因此从不命中，具名 `dot` 图在深色主题下一直垫着一张白纸底。
- **写在根 `<svg>` 上的 `style` 不再被吃掉。** 见下一节第 3 条。

### 会看到的变化（手写 `svg` 车道请读这里）

以下三条会**改变已有文档的渲染结果**。如果你只用 `dot` / `graphviz` / `mermaid` 车道，通常只会
看到「深色下终于看得见了」这一个变化。

1. **作者显式写的纯白 → 映射到主题背景色**（此前原样保留）。
   一块 `fill="white"` 的形状，在浅色主题下几乎看不出差别（背景色本身就接近白），但在
   **深色主题下会变成深色底**。这是刻意的：Graphviz 默认给节点写 `fill="white"`，只把黑改掉
   会让深色主题变成白底白字——换一种形式的同一个 bug。纯黑同理映射到主题前景色。
   **半透明不动**：`rgba(0,0,0,.5)` 原样保留，改写它会丢掉 alpha。

2. **谁都没声明 `fill` 时，根 `<svg>` 会补上 `fill="currentColor"`**，靠继承流下去。
   此前 `<circle stroke="currentColor"/>` 这类没写 `fill` 的形状恒为黑（SVG 的初始值），
   深色下是一枚看不见的黑饼；现在它跟随主题前景色。用的是**表现属性 + 继承**，而继承是层叠里
   最弱的一环，所以**作者的任何声明都赢**——元素自己写的、祖先继承的、SVG 内部 `<style>` 里
   写的、`<use>` 引用处写的颜色，在正常渲染里全部原样保留。（唯一的例外在遮罩内部，见本节
   末尾的限界说明。）

3. **不再往作者的根 `<svg>` 注入响应式尺寸的内联 `style`。**
   那条声明与 `theme.css` 的 `.mv-diagram svg { max-width:100%; height:auto }` 完全重复，
   全屏缩放也不依赖它；而它有实际害处：旧实现是在**字符串**上再拼一个 `style` 属性，作者若
   自己在根上写了 `style`，HTML 解析规则只保留第一个，于是**作者写在根上的整个 `style` 被静默
   吃掉**。现在我们对作者的根节点**一个字都不改**。宽图不溢出与全屏缩放均已复测无影响。

`<mask>` / `<clipPath>` 子树**不参与**颜色语义化——那里的黑白是遮罩亮度语义而不是颜色，按
「白→背景色」改写会让遮罩随主题变形。这些容器上会把「如果我们从没改过颜色、这里本该继承到的
字面值」钉回去（`fill` 与 `stroke` 都钉），所以常见情形下遮罩效果与改动前一致。

**一个限界，如实说明**：这层隔离是启发式，不是保证。我们看得见表现属性与内联 `style`，但
**看不见 SVG 内部 `<style>` 里的规则**（在这一层没有 CSS 选择器匹配）。所以当你用内部
`<style>` 给遮罩的祖先设 `fill` / `stroke` 时，我们选择**完全不动**那个遮罩——你的 CSS 本来就
赢过我们注入的缺省值，动它只会弄坏它；代价是这种写法下遮罩可能随主题变形。如果你的图正好
是「内部 `<style>` 上色 + 遮罩」这个组合，请在两种主题下各看一眼。

**已知取舍**：少数**非法** CSS 颜色写法仍会被判成黑（例如 `rgb(0,0,0,)`、逗号语法里亮度不带
`%` 的 `hsl(0,0%,0)`）。浏览器本来就会整条丢弃非法声明并回落到继承值，而继承到的通常正是我们
在根上补的 `currentColor`，肉眼无差；唯一还会咬人的是「祖先声明了颜色」那一种。
`lab()` / `oklab()` / `oklch()` / `color()` 刻意不解析——亮度轴语义不统一，猜错会改坏作者的
颜色，漏判的方向是「原样保留」，是安全的那一侧。

- **CLI 契约向后兼容**：没有删除或改名任何 flag，没有改动任何既有退出码，`mdxv` / `mdxx` 的
  既有用法一律不变。`--check` 是纯新增。
- **组件、组件参数、frontmatter 字段本次零改动**，所以按组件速查对齐本包的下游消费者无需改动。
- **新增一个显式依赖** `unist-util-visit-parents@^6.0.0`。它此前已作为传递依赖存在于安装树里，
  所以实际下载内容基本不变，但 `package.json` 的依赖清单确实多了一项。
- 导出产物仍然**零外链**、自包含。
- Node 要求不变：`>= 20`。
